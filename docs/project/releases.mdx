All six libraries share a stable version under npm's `latest` tag. Check
[npm](https://www.npmjs.com/package/@toolgrain/mcp) for the current version and
[package releases](https://github.com/keshavkatwe/toolgrain/releases) for release notes.
The historical [v0.1.0 release](https://github.com/keshavkatwe/toolgrain/releases/tag/v0.1.0)
and [RC0 prerelease](https://github.com/keshavkatwe/toolgrain/releases/tag/v0.1.0-rc.0)
remain available. `next` still points to RC0.

Changesets automation is active on `main`, with package-local changelogs and
package-scoped GitHub releases.

The publication workflow owns main-branch verification. It calls ordinary scoped
CI/support checks when no publication is planned, and complete release verification
when publishing. This avoids duplicate baseline/platform runs on release commits.
The `publish.yml` filename, `npm` environment, and trusted-publisher bindings stay
the same.

## Record a change

Run `bun run changeset` for a user-facing library change. Select affected
libraries, a bump type, and write release notes that explain the behavior and any
migration steps. Include the Markdown record with the implementation when
committing is authorized. Use `bun run changeset --empty` for repository-only
changes that need no library release.

Release PR versioning consumes all Changeset records. Keep that state when fixing
a versioned Release PR: the pinned action selects no publication when only empty
records remain. Consume an empty record during versioning rather than carrying a
fresh one into the release merge.

The pinned Changesets CLI 3.0.3 selects versions and updates dependencies. The
seven library workspaces form one explicit fixed group in `.changeset/config.json` and
share a version; their manifests are the source of truth. Examples and repository
tooling are unpublished npm workspaces and are ignored by Changesets. During
`0.x`, compatible fixes use patch records, while features and breaking changes
use minor records. From `1.0`, follow semantic versioning. The
[support policy](/project/support-policy),
including minimum increases and removal notices, still applies.

`bun run release:status` previews the pending plan. Package-local `CHANGELOG.md`
files are generated by Changesets and become the source for release notes.
Review their summaries and migration guidance in the Release PR. The root
[CHANGELOG.md](https://github.com/keshavkatwe/toolgrain/blob/main/CHANGELOG.md) preserves the historical RC0/0.1.0 notes; it is
no longer a second release ledger that must be edited for each change.

## Plan a release

Develop each feature on its own branch and reviewed PR, with tests, documentation,
and a Changeset. Choose a small release scope: one feature or a few related
features that can be accepted together. Use one temporary `prerelease/X.Y` branch
to assemble the selected commits and prepare test packages.

| Stage | Example version | Purpose |
| --- | --- | --- |
| Alpha | `0.3.0-alpha.0` | Test selected features while the release is still being built; add reviewed features in later alphas |
| Beta | `0.3.0-beta.2` | All planned features are included and APIs are settled; focus on fixes and combined application testing |
| RC | `0.3.0-rc.3` | Final candidate for stable publication; repeat acceptance after any changes |
| Stable | `0.3.0` | Accepted implementation, published through the reviewed stable Release PR |

All libraries in the fixed group share each version. Alpha, beta, and RC use matching npm tags;
stable `latest` and historical `next` stay unchanged during prerelease testing.
Every stage retains the full release verification and post-publication checks.
The pinned Changesets CLI continues its numeric counter across stages: for
example, `alpha.0` → `alpha.1` → `beta.2` → `rc.3`. Use the version it generates.
Freeze the feature scope at beta. Adding a feature after that point reopens the
scope and requires renewed combined testing. An individual feature's acceptance
does not establish acceptance of the combined release.

### Where to make changes

Make implementation fixes in the original feature branch and PR, then bring the
new commits into the same series branch and publish a new prerelease version.
Only release preparation, such as versions, generated changelogs, prerelease
state, and manifest tags, belongs directly on the series branch. Keep feature PRs
open until acceptance so their fixes can reach `main` through ordinary review.

For example, fix progress on its original feature branch, bring that commit into
`prerelease/0.3`, and publish the next `0.3.0-alpha.N`. Alpha is a release stage,
not another required branch. The same series branch later produces beta and RC.
Install exact published versions when recording test results.

After RC acceptance and explicit stable-release authorization, merge the approved
feature PRs into `main` and review the ordinary Changesets Release PR. Verify that
the stable implementation matches the accepted RC. Keep candidate metadata off
`main`; do not merge the series branch into it.

Agreement on the strategy does not authorize publication, feature merges, or a
stable release. Each prerelease requires confirmation of its prepared version
and full commit SHA. The reviewed stable Release PR remains the stable
publication gate.

## Automated release PR and publication

The `npm publication` workflow runs on pushes to `main`, using Changesets Action
v2.1.2's native `select-mode`, `version`, `pack`, and `publish` subactions. Its
commit is pinned; CLI and Action upgrades must be reviewed together.

1. Merge an ordinary reviewed change with its changeset. Changesets creates or
   updates **Release Toolgrain packages** on `changeset-release/main`.
2. The bot runs `bun run release:version`, consuming records, updating all library
   versions/dependencies and package changelogs, and synchronizing Bun workspace
   versions. Review that diff and the CI results. With `GITHUB_TOKEN`, GitHub can
   require a maintainer to **Approve workflows to run** for bot-created PR runs;
   approve those runs during review. No personal token is required.
3. Merge the reviewed Release PR when ready to publish. **This merge approves
   automatic npm publication, package tags, and GitHub releases.** The workflow
   does not auto-merge the PR. Bot version commits/PRs are authorized by this
   automation policy; local agent commits still need an explicit user request.
4. On the merged main commit, the workflow runs Release verification: baseline,
   the full supported runtime/platform matrix, intermediate TypeScript versions,
   and stable dependency drift. Supported failures block publication; Node 26
   and prerelease probes remain informational.
5. A separate job builds the libraries, checks contents and size budgets, and
   uses Changesets to create packed archives and its publish-plan artifact.
   Only the publish job gets OIDC permission. It publishes those archives to npm
   under `latest`, pushes package tags, and creates package-scoped GitHub releases from
   their package changelogs. Names follow `@toolgrain/mcp@0.1.1`, for example.
6. Post-publication checks verify all library `latest` tags in full and installer npm
   metadata, registry integrity, and downloaded archive bytes against the packed
   artifact. Fresh npm/Node and Bun consumers then check all library imports,
   minimum/current declarations, and the stdio/HTTP runtime flows. Reports are
   retained as workflow artifacts. A post-publication failure needs investigation;
   npm publication cannot be rolled back by a failed check.

No local version bump, manual npm publish, combined `vX.Y.Z` tag, or separate
GitHub release command is needed for this flow. The existing `v0.1.0` and RC0
release records are preserved. Repository-only changes use empty changesets and
do not select a library release. User-facing changesets create or update the next
automated Release PR.

## npm publication setup

The existing published libraries use public access, the explicit npmjs
registry, and stable `latest` configuration. The workflow retains filename
`publish.yml`, environment `npm`, and the six validated trusted-publisher
bindings for `keshavkatwe/toolgrain`. No npm token secret or local login is
required. The environment currently permits only main; it has no required reviewers.

The new `@toolgrain/react` workspace participates in version alignment and package
verification. Its first alpha uses the verified maintainer-publication path
below; subsequent CI publication requires its own reviewed trusted-publisher
setup. The workflow filename, `npm` environment, and existing publisher bindings
remain unchanged.
The reviewed Release PR is the stable publication gate. A prerelease needs an explicitly
allowed, exact prerelease branch as described below; do not broaden this to all branches.

GitHub Actions must be allowed to create pull requests in repository settings
(**Actions → General → Allow GitHub Actions to create and approve pull requests**).
Keep default workflow permissions read-only. The version job requests
pull-request write access; the reused baseline retains its PR-report permission.
The workflow never approves reviews itself.

External workflow Actions are pinned to full upstream commit SHAs. When updating
an Action, verify the new commit in its canonical repository and update every
reference, including composite actions. The repository's Actions allowlist must
permit the new pin before workflows use it. Enable the full-SHA policy only after
all active workflow branches use pinned references.

The active tag ruleset blocks updates and deletions for every tag, without bypass
actors. New release tags can still be created by the publication workflow.

The source repository is public, so publications automatically request
npm provenance. RC0 and 0.1.0 were published without provenance while the source
was private. All six trusted publishers completed their first successful OIDC
publication for 0.1.0; a new or replacement binding must complete its first
successful publish within npm's two-day validation window.

Changesets does not currently support Bun natively. The workflow-only npm
adapter preserves the native planner, packed-artifact format, publishing order,
tag reporting, and GitHub release handling. It uses Bun 1.3.14 to pack archives
with rewritten `workspace:*` dependencies. Registry reads and npm 11.21.1 archive
publication run outside the checkout, where npm does not encounter the
repository's intentional Bun `devEngines` requirement. Archive lifecycle scripts
are disabled. Ordinary development continues to use Bun.

`release:version` retains the existing narrow Bun workaround: Bun 1.3.14 leaves
stale workspace versions during lockfile-only installs, and packing reads them.
The helper synchronizes only the library version fields, preserving external
resolutions. `bun run release:check [--version X.Y.Z]` checks manifest/lock
alignment. It does not select versions or write changelogs.

## Failures and recovery

Six-package publication is not atomic. Inspect the run, its plan/archive
artifacts, npm versions/tags, and GitHub tags/releases before recovery. Never
unpublish or replace an existing version. The manual **Run workflow** action on
main runs the same planner and all verification gates; it does not bypass them.
Prefer a fresh run after checking partial state so Changesets can replan around
already-published versions, rather than replaying a stale packed publish job.
Existing remote tags with missing GitHub releases need explicit inspection and
repair; the native action does not guarantee recreating missing release records.

A maintainer can still dispatch **Release verification** on main with an expected
version without publishing. Local preparation can use `release:status`,
`release:version`, and `release:check` in a disposable checkout; do not version
main manually alongside the bot's Release PR.

## Verify a release candidate before stable publication

Stable publication uses the reviewed Release PR on `main`. Prerelease
publication is a manual dispatch from one protected branch per release series,
for example `prerelease/0.3`. All libraries in the fixed group share each prerelease version,
such as `0.3.0-alpha.0`, and publish under its matching `alpha`, `beta`, or `rc` tag. Stable `latest` and
historical `next` stay unchanged.

Keep the `publish.yml` filename, `npm` environment, and existing trusted-publisher
bindings. In the environment's deployment-branch settings, allow `main` and only
the exact active series branch. Restrict updates to trusted maintainers and
review changes to publication code. A feature branch or a per-version branch
such as `prerelease/0.3.0-alpha.0` cannot publish through this prerelease path.

### Prepare and publish a candidate

1. Review the release infrastructure independently of the feature. Keep the
   selected feature PRs in draft while preparing and testing prereleases.
2. Create the series branch from the reviewed infrastructure plus the selected
   feature commits. For early testing, run `bun run changeset pre enter alpha`, then
   `bun run release:version`. Set `publishConfig.tag` to `alpha` in all library
   manifests. Changesets selects versions and changelogs; `release:version`
   aligns the Bun workspace metadata. Commit the prepared state when authorized.
3. Run the full local checks, push the series branch, and record its full commit
   SHA and version. Manually dispatch **npm publication** on that branch with
   both `version` and `expected_sha`. For example:

   ```sh
   gh workflow run publish.yml --ref prerelease/0.3 \
     -f version=0.3.0-alpha.0 -f expected_sha=FULL_PREPARED_COMMIT_SHA
   ```

4. The workflow rejects missing or mismatched inputs, the wrong release series,
   a stable version on a prerelease branch, and any mismatch between the version's
   stage, Changesets prerelease tag, and all library manifest tags. Pushes alone
   do not publish. The run uses the exact triggering commit so npm provenance
   identifies the verified candidate. Moving the branch does not change an
   already-dispatched run's source; an expected-SHA mismatch fails the run.
5. The existing complete release verification runs before packing. Publication
   uses those packed artifacts, validates their package/version/tag plan, and
   retains a `publication-manifest` artifact containing the source SHA, workflow
   run, and package archive identities. Post-publication checks verify all library
   versions under the selected tag, unchanged stable `latest` in both npm metadata formats, archive
   integrity, and fresh Node/Bun consumers.
6. Install the exact candidate in the real application. Record the requirement,
   installed version, source SHA, workflow run, and observed result on the feature
   PRs. For the OAuth change, check automatic scope selection, fresh CIMD/DCR
   authorization and consent, refresh/retry, tool access, and removal of the
   response-enrichment workaround. Local token tests do not replace these checks.

The manual dispatch approves only the specified prerelease. For ordinary manual stable
recovery on `main`, leave both prerelease inputs blank; supplying them on main is rejected.

### Introduce a new package during an alpha series

The `0.3.0-alpha.2` preparation combines [progress (#56)](https://github.com/keshavkatwe/toolgrain/pull/56),
[fixed resources (#59)](https://github.com/keshavkatwe/toolgrain/pull/59), and
[native MCP Apps/React (#60)](https://github.com/keshavkatwe/toolgrain/pull/60).
These feature PRs remain open. All seven packages
use the same candidate version and `alpha` tag. Stable `latest` remains `0.2.0`
for the six established packages. npm also assigns `latest` on a package's first
publication, even when `alpha` is requested, and rejects removing it. React's
initial `latest` therefore points to `0.3.0-alpha.2`; it is a prerelease, not an
accepted stable release. Install exact candidate versions during acceptance.

List new packages explicitly in `.changeset/initial-publications.json`. The
prerelease guard captures a per-package latest baseline in both npm metadata
formats. For a listed package with no stable history, explicitly pin its first
candidate in `.changeset/initial-latest.json`. This preserves npm's required
initial tag without allowing later candidates to move `latest`. The observed
registry metadata also included a `0.0.0-stage` placeholder; the guard permits
that entry only alongside an explicit pin. Do not create a placeholder yourself.
Missing established packages, differing
stable versions, unapproved initial tags, hidden stable history, invalid metadata,
and registry failures still stop the release. Post-publication checks verify the
exact per-package snapshot as well as archive bytes.

Run **Release verification** on the prepared series branch with its exact version.
After the complete release checks, its `verified-initial-publications` artifact
contains the real React archive and a manifest recording the source SHA and hash.
Check that SHA against the prepared candidate before using the archive. This
workflow has no publication job, npm environment, package tags, or GitHub releases.
Normal publication refuses a still-unpublished initial package before reaching
any publish job, so omitting that first publish cannot start publishing the group.

npm requires an existing package before configuring its trusted publisher; see
the [npm trust prerequisites](https://docs.npmjs.com/cli/v11/commands/npm-trust/#prerequisites).
After explicit publication approval, a maintainer publishes the real, verified
React candidate archive from that artifact under `alpha` once. Do not publish a
placeholder or invent a stable version. This maintainer publication has no
automatic CI provenance; retain the verified archive hash and publication receipt.
For the next legitimate React candidate, configure its trusted publisher for
`keshavkatwe/toolgrain`, workflow `publish.yml`, environment `npm`. Existing
publisher bindings and environment rules stay unchanged. Time the binding for
that candidate's first OIDC publish within npm's documented expiry window;
do not invent another release just to validate a binding.

The first React publication confirmed npm's `latest` behavior in both registry
metadata formats. Authenticated `npm dist-tag rm @toolgrain/react latest` returned
HTTP 400; the [npm CLI report](https://github.com/npm/cli/issues/8490) describes the
same first-publication behavior. The original absent-latest guard correctly
stopped the remaining packages. Recovery requires a reviewed tooling correction
and approval of its new source SHA. Keep the original first-publication archive,
source SHA, and hash; do not republish React or change library contents under the
same version.

Dispatch normal publication on the same source SHA only after this setup is
complete and approved. Changesets skips the already published React version;
verification still compares its bytes with the reviewed
initial-publication archive. Nothing may republish an existing version.

The combined MCP archive measures approximately 110.6 kB packed and 438.5 kB
unpacked. Its combined-feature limits are 110 KiB packed and 440 KiB unpacked;
content, legal-file, source-map, and coverage checks remain enabled.

### Move from alpha to beta or RC

Use the same `prerelease/X.Y` branch throughout the series. To change stages,
edit the `tag` in `.changeset/pre.json` to `beta` or `rc`. Version the next feature
or fix Changeset with `bun run release:version`. Changing the tag alone does not
advance the package versions. If no implementation Changeset is pending, use
`bun run changeset` on the series branch to add a patch record that accurately
describes the stage transition, then run `bun run release:version`. This release
preparation record stays on the series branch and is excluded from main.

Set `publishConfig.tag` in all library manifests to the same stage. Let Changesets
select the versions; do not rename manifest versions
or relabel an existing published archive. Review the prepared diff and dispatch
with the resulting exact version and full source SHA when authorized.

Each stage publishes a new immutable version under its matching tag. Other
prerelease tags keep their previous versions, and `latest` remains stable. Beta
requires the complete selected feature set; stable publication requires successful
RC acceptance and the separately reviewed stable Release PR.

### If the published candidate fails the requirements

Fix the original feature PR and add a regression test. Bring the fix and its new
Changeset into the same series branch, then run `bun run release:version` again.
The next candidate advances, for example, from `0.3.0-alpha.0` to `0.3.0-alpha.1` across all aligned
libraries. Review the prepared diff, commit/push when authorized, and dispatch
with the new version and full SHA. Repeat all publication and acceptance checks.
No new release branch or environment permission is needed for each candidate.

Never overwrite or unpublish the previous candidate. Its stage's npm tag moves to the new
candidate after publication; `latest` remains on stable. A partial publication
is not an accepted candidate: inspect all library registry versions and the original
workflow's plan/artifacts before recovery. Never reuse a published candidate
version for changed source. Keep the exact commit and verified artifact identities
when recovering a partially published run.

### Release stable after acceptance

Keep candidate version commits, `.changeset/pre.json`, consumed prerelease
Changesets, and prerelease manifest tags off main. Once the final RC passes real-application
acceptance and stable publication is explicitly authorized, merge the reviewed feature PRs and
use the ordinary stable Changesets Release PR.

Check that the stable package implementation matches the accepted candidate,
allowing the intended version, internal dependency version, and changelog changes.
A further runtime, external dependency, or exported-API change requires another RC.
Run the full stable release checks on the exact final commit. Merging the reviewed
Release PR remains stable publication approval; do not merge the RC branch or
point `latest` at an RC version. Remove the series branch's environment permission
when that series is complete.

Do not repeat the initial 0.0.0 bootstrap used to select RC0. The stable baseline's documented client
limitations remain in the [published-package verification](/compatibility/published-packages).
