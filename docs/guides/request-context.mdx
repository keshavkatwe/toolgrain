---
title: "Request context"
description: "Read request metadata, observe cancellation, and report progress from tool handlers."
---

Handlers receive a second argument, `ctx: ToolContext`. Use it for cancellation, progress, and request information without making the tool definition specific to a server or auth provider.

```ts
import { tool } from "@toolgrain/mcp";
import { z } from "zod";

const lookup = tool({
  input: z.object({ id: z.string() }),
  async execute({ id }, ctx) {
    ctx.signal.throwIfAborted();
    console.error("lookup", ctx.request.id);
    return { id };
  },
});
```

## Fields

| Field | Meaning |
| --- | --- |
| `signal` | AbortSignal for the active request |
| `reportProgress(update)` | Bound asynchronous progress reporter; no-op without a client token or delivery channel |
| `request.id` | JSON-RPC request ID |
| `request.protocolVersion` | Selected supported revision |
| `request.client` | Optional self-reported client info and capabilities |
| `request.meta` | Deeply frozen copy of request `_meta`, empty when absent |

`request`, its metadata, and any client details are frozen per-request copies. Changing data in one request cannot mutate another request's snapshot. Client details are unverified and are absent where the transport and era provide none, such as legacy HTTP. Never use a client name or capability declaration as an authenticated identity.

Client info/capabilities use a readonly union of modern and legacy wire types. `ToolRequest` is not a discriminated union: checking `protocolVersion` does not narrow the client type. Guard fields that differ between eras.

## Application data

Use [context providers](/guides/context) for services such as database access, and integration-specific [auth accessors](/authentication/overview) for verified identity. `ToolContext` itself remains non-generic. Provider accessors return promises; JWT and Clerk `useAuth(ctx)` accessors remain synchronous.

## Constructing a context for tests

```ts
import { toolContext } from "@toolgrain/mcp";

const ctx = toolContext({ request: { id: "test-1", meta: { source: "test" } } });
const value = await lookup.execute({ id: "u_1" }, ctx);
```

The helper defaults omitted fields independently: ID `0`, the modern revision, no client, empty metadata, a fresh signal, and no registered providers. Reusing one context reuses its provider cache. Use the helper rather than hand-building context objects; future fields may be supplied by the helper. Direct calls bypass server validation and authorization.

## Report progress

Tool handlers and context providers can report progress during an active invocation:

```ts
const processFiles = tool({
  input: z.object({ files: z.array(z.string()) }),
  async execute({ files }, ctx) {
    for (let index = 0; index < files.length; index++) {
      ctx.signal.throwIfAborted();
      // Perform application work for files[index], observing ctx.signal.
      await ctx.reportProgress({
        progress: index + 1,
        total: files.length,
        message: `Processed ${index + 1} files`,
      });
    }
    return { processed: files.length };
  },
});
```

The MCP client opts in with a string or integer `params._meta.progressToken`.
Toolgrain attaches that token to `notifications/progress`. Without a token or
delivery channel, reports resolve without sending. `toolContext()` uses that
no-op behavior for direct calls. Tool results retain their normal validation and
conversion.

Progress values must be finite and strictly increase. `total` and `message` are
optional; values may be fractional. Await reports to respect backpressure and
use `ctx.signal` to stop application work on cancellation. Reports after completion
or cancellation send nothing. The bound method can be passed as
`reportProgress: ctx.reportProgress` to application helpers alongside `ctx.signal`.

Stdio uses its existing message channel. HTTP opens a POST SSE response on the first
progress update, sends the final response on the same stream, and ends it. Calls
that send no updates retain JSON responses. Progress belongs to the individual
request and does not require `subscriptions/listen`. Client UI presentation is
separate from protocol delivery; the dated client compatibility reports do not
verify progress displays.
